# S7 ZLG 与共享 CAN 静态复核

2026-11-17，V08 为 MANUAL。按用户范围只查看与整改 ZLG 和共享调用。九份受影响 Python 文件通过 `ast.parse`，只读取源码。没有运行 CAN 测试、回环模拟、SDK 加载或实机操作。恒润专有发现 A18、A30 保留在原审计中。

- A14：[SDK 装饰器](../../backend/zlg/FunctionRely.py)保留正常返回，捕获普通异常并以带原始原因的异常向上传递，未拦截进程退出异常。[Windows 接收与包装器](../../backend/zlg/zlgcan.py)把接收计数 0 视为空队列，拒绝 SDK 无效计数及越界读取结果；设备属性查询保留其官方接口中的空指针语义。
- A15：[服务关闭与断线](../../backend/app/can_service.py)停止接收、清除发送归属、下线旧引用，失败时保留清理重试对象。新打开先处理待释放资源。Windows 独立尝试各通道和设备关闭；macOS 独立尝试停通道、停止设备、释放接口、关闭 USB 及日志。外层尽力停止周期任务、关闭 BLF、接收线程、后端、DBC 和日志，并汇报失败。驱动是否实际释放仍取决于 SDK。
- A21：[历史监控入口](../../backend/zlg/zlgcan.py)保留调用名，整数及十六进制字符串统一转换成 29 位范围内的 ID。根据 DBC 区分标准和扩展帧，跳过不同 ID、不同帧类型及远程/错误帧。匹配的有效负载才参与信号值和响应规则。
- A23：[SDK 路径](../../backend/zlg/native.py)供加载器和 [便携自检](../../tools/windows/launcher.py)复用。Windows x64 缺少可选 `backend/zlgcan_x64/zlgcan.dll` 时只提示，通用启动继续。需要该后端时才通过 Windows x64 平台检查和加载库。分发说明要求使用获许可的 SDK。
- A29：[发送所有权](../../backend/app/can_service.py)在预检及运行时以通道和报文名判断。手动发送、定时触发、脉冲、唤醒和 UI 都经过同一资源冲突检查。触发相位的等待期间仅占用本键。UI 停止及收尾只处理同一连接、同一拥有者和仍匹配的循环对象。设备断线时清除所有登记。
- A31：[台架 CLI](../../backend/tools/can_bench.py)先检查有限正时长和通道，再访问本地监听器或后端。inf、nan、零均在设备访问前返回错误。合法时长进入既有运行逻辑，时间终止及中断走清理。
- A32：[历史配置字](../../backend/Functional/Functional.py)保留公开名称并调用底层接口。底层发送和接收使用同一受支持的 CAN0。读取按字节列表校验服务、DID 和帧序号；写入先验证 200 字节，同步等待会话、访问控制、流控及写入确认。缺回应或协议无效会明确失败，原始参数列表保持不变。
- A33：[Windows 通道初始化](../../backend/zlg/zlgcan.py)区分可选控制器时钟和必需 CAN FD 模式、波特率、终端、合并接收。可选项被拒记录警告，任一必需项、接口释放、缓冲区清理或通道启动失败均不得登记通道。已取得且复位未确认的句柄保留到关闭流程。实际 SDK 属性支持和设备状态未实测。

以上为代码结论。Windows 通用便携包的原生验收仍按 V11 独立进行。
