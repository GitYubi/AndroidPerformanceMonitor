# CAN 总线接入与验收记录

来源：GitYubi/ZcanServer，固定提交 `4d88a641ae0d1eb33c67d84fe18b015f9b97e5c3`。核心包在 `backend/zlg` 和 `backend/Functional`，示例 DBC 在 `backend/config`。目标为 FastAPI 单进程服务和 React 工作台，不需要源项目 Qt。现有 Android ADB 设备管理与 CAN 设备分别由各自服务持有；没有发现需对外兼容旧 ZCAN TCP 协议的需求，因此未启用独立 TCP 监听。

## 运行

安装 `backend/requirements.txt`，使用项目原有 `./run-local.sh`，在导航栏打开“总线控制”。默认明确选择模拟，可输入绝对 DBC 路径，留空使用示例。Mac USB 选择 Mac USB，需本机安装匹配架构的 libusb；硬件只应在接好总线和确认配置后使用。后端可直接通过 `/api/can` HTTP 路由或 `app.state.can` 进程内调用；旧 `Functional.zlgCanFuncs` 入口保留。数据默认写在 `backend/data/zcan`，也可在启动前设置 `ZCAN_DATA_DIR`。工作目录不影响资源路径。工作台提供发送、接收、任务、录制页；记录为 BLF，保存在数据目录下的 `can_log`。

服务按通道和报文名管理任务，接收由单一采集线程分发到带序号的有界缓存，各消费者可按 `after` 独立读取，BLF 在后端逐帧写入。发送次数指软件提交次数；时间触发以周期控制触发和复位阶段，两者不等同于独立节点实际收到的帧数。普通发送未指定信号使用物理零，唤醒和脉冲使用 DBC 初始值或原始零；不自动生成车型 E2E/CRC/计数器。`can_log_fail` 没有故障前历史缓存，录制仅覆盖开始之后的数据。接收缓存有限，落后消费者可能丢帧；BLF 才是逐帧记录。当前没有独立 TCP 服务。

## 记录与限制

- 软件环境：macOS ARM64，Python 3.12.0；示例 DBC。模拟测试、USB 协议替身及 BLF 读取的结果以执行时测试输出为准。
- USB 替身不代表实物。尚未验证终端电阻、独立接收节点、真实周期、回显或 BLF 绝对时间；Windows SDK 和设备也未验证。部署 Windows SDK/libusb 时需另行处理供应商文件及许可证。
- 源项目测试中直接依赖 Qt 和旧 TCP 的部分未作为后端测试引入；核心协议替身测试单独保留。Windows 硬件周期发送尚未实现。

## 2026-11-11 实机检查

在 macOS ARM64、Python 3.12.0、PyUSB 1.3.1 与 Homebrew libusb 1.0.30 环境中，通过 USB 查询发现一台 VID `0x3068`、PID `0x0009` 设备。设备报告型号 `USBCANFD-200U`、协议 `0x0119`、硬件 `0x0300`、固件 `0x0235`、CAN 通道数 2，与后端配置一致。通过目标 FastAPI 入口以 `mac-usb` 打开设备（不打开 CAN 通道），确认硬件定时能力标识并正常关闭。该检查没有发送 CAN 帧，也没有验证通道、实际总线收发、定时精度、触发、BLF 对时或独立接收节点。

## 实机单帧发送

使用用户指定的台架 DBC，Mac USB 通道 0 打开成功。向标准 ID `0x287` 的 CAN FD 报文 `BDCU_SWS_0x287` 提交一帧 `VolDwn=1`，BRS 关闭，数据为 `00 40 00 00 00 00 00 00`。设备返回一帧标记为 TX 的回显，随后关闭通道和设备。该结果证明本机提交和设备回显，不证明独立接收节点收到或车机执行；未进行周期频率或 BLF 对时验收。

## 实机硬件定时与 BLF 检查

使用用户确认可用的 `BDCU_SWS_0x287`、通道 0、CAN FD、50 ms，硬件定时发送 `VolUp=1` 约 250 ms，再更新为 `0` 约 250 ms，最后停止并关闭设备。更新前后均使用硬件槽 0，停止后任务列表为空。设备回显 11 帧：前 6 帧为 `1`，后 5 帧为 `0`，相邻设备时间戳约 50 ms；BLFReader 从 `hardware_periodic.blf` 读到同样的 11 帧 TX 记录。上述为设备回显和本机 BLF 证据，未用独立节点测量总线接收，也未完成 BLF 绝对时间对时验收。

## 实机时间触发检查

通道 0、`BDCU_SWS_0x287.VolUp`、CAN FD、100 ms、`isBreak=True` 调用时间触发入口。调用返回成功，耗时约 222 ms；设备回显按顺序为 `1、1、0`，间隔约 100 ms，随后任务列表为空并关闭设备。触发阶段为按时间保持，设备帧数由周期和切换时点决定；本次未使用独立接收节点。`isBreak=False` 与触发期间被更新或停止的实机行为仍待验证。

## 实机后续验证（通道 0）

- 触发 `VolUp=1` 期间更新为 `0`：旧触发返回 0（被接管），新任务持续发送复位值且未被旧流程停掉，随后主动停发。
- 触发 `VolDwn=1` 期间手动停止，再提交 3 帧 `VolDwn=0`：旧触发返回 0；回显为 1 帧触发值和 3 帧复位值。
- 收发中的关闭与重新打开：关闭前有硬件周期任务；关闭后任务为空，重新打开并观察约 400 ms 未见该报文的 TX 回显。未模拟物理拔线。
- 接收及 BLF：1.5 秒录制得到 355 帧，均为通道 0 RX CAN FD BRS，所有 BLF 帧的时间戳、ID、通道、方向、FD/BRS 和数据均能在同次接收缓存中找到；包含同 ID 多帧。录制后缓存继续收帧，缓存总数 366 并非同一录制边界的统计。首帧时间比录制开始后的主机时间晚约 21 ms，尾帧比停止返回时间早约 10 ms，仅作粗略一致性检查，不是独立时钟精度测量。
- 通过目标 FastAPI 的真实 HTTP 服务打开设备、启动录制、有限发送 3 帧 `VolUp=0`、读取帧、停止录制和关闭设备；观察到 3 帧相应 TX 回显。
- 根据用户要求暂不测试通道 1。总线页面连接选项默认只打开通道 0，可显式选择通道 1。页面浏览器自动化工具未能启动，界面实际视觉与交互仍待检查。多个不同报文同时发送需要用户提供可安全发送的第二个报文；异常物理拔线、独立接收节点验证及 Windows 实机仍待覆盖。

## DBC 浏览和唤醒界面补齐

DBC 选择器现在从目标项目目录开始，支持上级目录、进入子目录和文件夹路径跳转；点击 DBC 即解析，无需打开设备。页面显示解析数量、报文搜索和下拉选择、信号物理范围/步长/单位/枚举/注释。发送支持批量信号、CAN FD/BRS、周期、有限次数、时间触发和按次数脉冲。

唤醒配置按 DBC 内容 SHA-256 单独保存到数据目录 settings，可编辑多个报文信号，开始/取消唤醒复用源后端。支持导入原 ZCANServer 的 Qt wake.ini（不依赖 Qt）或 JSON 配置，导入时校验当前 DBC 和信号值。用户提供的生产 DBC 实际解析出 135 条报文和 1872 个信号；原 wake.ini 中匹配的 13 条唤醒报文已在模拟后端完成导入、启动、取消验证，未自动执行实物唤醒。设备连接后禁止切换 DBC，启动唤醒前重新核对 DBC 内容。
